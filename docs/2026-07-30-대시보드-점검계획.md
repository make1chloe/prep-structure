# 대시보드 점검 계획 → 시뮬레이션 → 수정 계획

> 순서: **① 무엇을 검사할지 정한다 → ② 시뮬레이션으로 실제 놓치는 것을 센다 → ③ 그 결과로만 수정 순서를 정한다.**
> 감으로 고치지 않는다. 시뮬레이션이 "놓쳤다"고 말한 것만 고친다.

## 왜 대시보드인가

기존 시뮬레이션 4종(`simulate-workflow/month/2weeks/inclass`)은 **오늘 수업·수강료·경고**를
검사한다. 정작 **하루를 시작하는 화면(대시보드)이 그날 알아야 할 일을 다 보여주는지**는
아무도 검사하지 않았다. 대시보드는 가장 자주 여는 화면인데 검사 사각지대였다.

## 검사 기준 — 두 가지 최우선 원칙

1. **사람이 한눈에 파악하고 바로 조작할 수 있는가**
   - 그날 알아야 할 일이 대시보드에 **뜨는가** (신호 커버리지)
   - 뜬 것을 **눌러서 바로 처리하러 갈 수 있는가** (막다른 태그 = 실패)
   - 학원이 지금 어떤 상태인지 **숫자 한 줄**로 보이는가
2. **중복 입력 · 중복 페이지가 없는가**
   - 같은 정보가 한 화면에 두 번 뜨지 않는가
   - 같은 데이터를 두 화면이 따로 보여주며 서로를 모른 척하지 않는가

## 검사 항목

### T1. 신호 커버리지 — `scripts/simulate-dashboard.mjs`

현실적인 하루(월말 이틀 전, 시험 일주일 전)를 데이터로 만들어 놓고,
"그날 원장님이 반드시 알아야 하는 일" 목록과 "현재 대시보드 규칙이 실제로 띄우는 것"을
**실제 라이브러리 코드**(`warnings` `tuition` `monthly` `wordTest`)로 대조한다.

심어둔 사건: 반성문 문턱 학생 · 보강 안 잡힌 결석 · 어제 발송 실패 · 어제 미발송 리포트 ·
월말 리포트 시점 · 시험 임박(범위 미등록) · 오늘 재시험 · 보강 필요 횟수 · 새 요청 · 새 댓글

### T2. 조작 거리 — 같은 스크립트에서

대시보드에 뜨는 각 신호가 `<Link>`(처리하러 감)인지 `<span>`(보기만 함)인지 센다.
`app/page.jsx`를 파일로 읽어 검사하므로 코드가 바뀌면 결과도 따라 바뀐다.

### T3. 중복 — 같은 스크립트에서

- 같은 정보가 배지와 카드에 **두 번** 뜨는 것
- `tasks` 한 테이블을 `/todo` `/tasks` 두 화면이 나눠 보여주는 것
- 일정이 네 곳(`tasks` `exam_periods` `holidays` `attendance.planned`)에 흩어진 것

### T4. 성능 — 같은 스크립트에서

`app/page.jsx`의 순차 `await supabase` 개수를 세서 직렬 로딩 시간을 추정한다.
(쿼리당 30~80ms 가정. 병렬로 묶으면 얼마나 줄어드는지 같이 계산)

### T5. 회귀 안전망 — 기존 검사 재사용

수정 후에는 반드시 `bash scripts/check-pages.sh` (미선언 변수 · use server export · 빌드)
+ 기존 시뮬 4종이 그대로 통과해야 한다. 대시보드 고치다 오늘 수업을 깨면 안 된다.

## 시뮬레이션 결과 (2026-07-30 실행)

`node scripts/simulate-dashboard.mjs` — 월말 이틀 전 화요일 아침을 재현한 결과:

> **그날 알아야 하는 22건 중 16건(9종)이 대시보드에 안 뜬다. 1건은 뜨지만 눌러도 갈 곳이 없다.**

| 신호 | 지금 | 원인 |
|---|---|---|
| 반성문 문턱 학생 | ✕ 안 뜸 | `lib/warnings.tally` 가 있는데 /today 문자 문구에만 쓴다 |
| 리포트 발송 실패 | ✕ 안 뜸 | /resend 만 안다 |
| 어제 미발송 리포트 | ✕ 안 뜸 | unsent 쿼리가 `eq(date, 오늘)` — 어제 것은 **영영** 안 보인다 |
| 오늘 재시험 | ✕ 안 뜸 | 집계 없음 |
| 시험 임박 (D-7) | ▲ 막다름 | '시험 전날 등원' 태그만, 링크 없음, 내신 전환 신호 아님 |
| 시험범위 미등록 | ✕ 안 뜸 | /prep 과 대시보드가 서로 모름 |
| 월말 리포트 시점 | ✕ 안 뜸 | `lib/monthly` 가 있는데 쓸 때를 아무도 안 알려줌 |
| 보강 필요 횟수 | ✕ 안 뜸 | `lib/tuition` 이 계산하는데 /tuition 에만 있음 |
| 미납 | ✕ 안 뜸 | **기능 자체가 없음** (payments 테이블 없음) |
| 요약 숫자(재원·출석률·발송률) | ✕ 안 뜸 | 대시보드에 숫자 지표가 0개 |

그 밖의 실측:

- **조작 거리** — 배지 모양인데 못 누르는 `<span className="btn">` 2개(학부모 알림 · 보강 잡을 것).
  특이사항 카드의 태그(결석 예정 · 미흡 학생)도 전부 링크 없음.
- **중복** — 보강 잡을 것 · 학부모 알림 · 스케줄 특이사항이 **같은 화면에 배지와 카드로 두 번**.
  `tasks` 한 테이블을 /todo 와 /tasks 두 화면이 나눠 보여줌. 일정은 네 테이블에 흩어져 있음.
- **성능** — `app/page.jsx` 에 `await supabase` **25회 전부 직렬**, `Promise.all` 0회.
  쿼리당 40ms 면 첫 화면 약 1초. 병렬이면 ~0.2초.

## 수정 계획 (시뮬레이션 결과로 확정)

우선순위 기준은 두 가지뿐이다: **사람이 한눈에 보고 바로 조작** · **중복 제거**.

### 1단계 — 안 뜨는 9종을 대시보드에 연결 (새 로직 거의 없음)

계산 코드는 전부 이미 있다. 대시보드에서 한 번 더 부르기만 하면 된다.

1. 반성문 문턱 학생 (`tally` 재사용) → 누르면 /today 그 학생
2. 발송 실패 + 지난 미발송 — unsent 쿼리를 `lte(date, 오늘)` 로 넓히고 실패 건 합산 → /resend
3. 오늘 재시험·보강 명단 → /today
4. 시험 D-7 진입 + 시험범위 미등록 학교 → /prep
5. 월말 마지막 3일에 "월말 리포트 준비 N명" → /monthly
6. 보강 필요 합계 (`studentAmount.makeupNeeded` 재사용) → /tuition
7. 요약 숫자 한 줄: 재원 N · 이달 출석률 · 리포트 발송률 (기존 테이블 집계만)

### 2단계 — 조작 거리 · 화면 내 중복 제거

- 배지와 카드가 **같은 데이터 배열 하나**에서 렌더되게 (원칙 1: 한 곳 입력 여러 곳 참조).
  배지는 전부 눌리는 링크로: span 2개 폐지.
- 특이사항의 모든 태그에 처리 화면 링크.

### 3단계 — 수납 신설 (없는 기능 중 유일하게 매달 반드시 하는 일)

- `0055_payments.sql` — 학생·월·금액·받은 날. **새 페이지를 만들지 않는다** —
  이미 금액을 계산하는 /tuition 안에 "받음" 체크로 넣는다 (중복 페이지 금지).
- 대시보드에 "미납 N건" 배지 → /tuition.

### 4단계 — 성능 + 시뮬 하드코딩 제거 (하나의 수정으로 둘 다)

- 대시보드 데이터 수집을 `lib/dashboard.js` 로 추출하고 `Promise.all` 로 병렬화.
- 그러면 `simulate-dashboard.mjs` 의 CURRENT_RULES 하드코딩도 **실제 함수 호출로 대체**된다.
  지금은 page.jsx 규칙을 시뮬에 옮겨 적어 둔 상태 — 이것 자체가 중복이므로 여기서 없앤다.

### ✅ /todo · /tasks 통합 — 완료 (2026-07-30)

두 화면은 **같은 테이블(`tasks`)** 을 `kind` 로만 갈라 읽고 있었다. 화면을 하나로 합치고
위에 **[통합] [일정만] [할일만]** 버튼을 뒀다. 셋 다 같은 페이지다.

- `/todo` → `/tasks?view=todo` 로 넘긴다 (옛 즐겨찾기·홈 화면 바로가기가 안 깨지게)
- 메뉴는 아홉 개 → 여덟 개. `할일` `일정` 두 줄이 `할일 · 일정` 한 줄이 됐다
- 대시보드의 `할일` `지난 할일` 배지도 `/tasks?view=todo` 로
- `revalidatePath("/todo")` 8곳을 `/tasks` 로 옮김 (안 그러면 자동 생성된 할일이
  화면에 바로 안 나타난다)
- 보는 화면만 합쳤고 **데이터는 원래부터 한 테이블**이라 이관·마이그레이션이 없다

### 참고 — 출결선생 · 결제선생 API (2026-07-30 문의)

API 키 발급에 50만원. **권하지 않는다.**

1. 연 사용액보다 연결 비용이 크다. 학생 수가 적으면 API 가 덜어주는 손도 적다
2. 출결은 앱에 이미 있다 → 연결하면 출결 기록이 두 군데 살아 있게 된다 (중복 금지 원칙 위반)
3. 수납은 **엑셀 내보내기가 되는지 먼저 확인.** 앱에는 이미 엑셀 업로드가 다섯 군데
   (학생·반·교재·단원·노션) 있어서 `/import` 에 탭 하나면 0원이다

입금 전 서면으로 확인할 것: 50만원의 성격(보증금 / 선불 충전금 / 발급 수수료),
환불 조건, 충전금이면 소멸기한, 계약 전 API 문서 열람 가능 여부, 해지 시 데이터 반출.

대시보드 시뮬은 수정 후 "안 뜨는 것 0건 · 막다른 것 0건"이 목표다.
