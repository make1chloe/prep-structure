# 클로이영어 앱 개선안

> 대상: chloe-english.vercel.app (Next.js + Supabase, `make1chloe/prep-structure`)
> 근거: 원장님 지적 + 공개 디자인 시스템·관리형 제품 7종·국내 학원관리 5종 실측 조사 (상세는 「클로이영어 앱 UI 가이드」)
> 작성일: 2026-09-11

---

## 0. 원장님 지적의 재정의

> "쓸데없는 메뉴 설명이 너무 많다. 설명이 필요하면 툴팁으로 빼면 되고, 애초에 설명 없이 작동하는 단순한 구조여야 한다."

이 지적은 맞지만, **설명문은 원인이 아니라 증상**입니다. 조사에서 확인된 메커니즘은 이렇습니다.

- 국내 학원관리 1위 제품(클래스업) 헬프센터 128개 문서 전수 분석 결과, **"청구서 생성"에 제목이 거의 같은 문서가 5개** 있었습니다. UI에 진입 경로가 5개라서입니다.
- **경로 수 = 도움말 수 = 설명문의 양.**

따라서 개선의 방향은 "설명문을 툴팁으로 옮기기"가 아니라 **설명문을 유발하는 구조를 제거하는 것**입니다. 툴팁으로 옮기는 것은 마지막 4순위이며, 조사한 세 디자인 시스템(Polaris·Carbon·Atlassian)이 모두 **"과업 수행에 필요한 정보를 툴팁에 넣지 말 것"** 을 명시합니다. 즉 툴팁은 원장님이 없애고 싶어 하는 설명문의 대체재가 될 수 없습니다.

## 1. 핵심 발견 — 스킬 문서가 곧 실패 지점 지도다

클래스업 역분석에 쓴 방법(**도움말이 많이 달린 화면 = 설명 없이는 못 쓰는 화면**)을 클로이영어 앱에 그대로 적용하면, 답은 이미 나와 있습니다.

`chloe-english-app` 스킬 문서에 적혀 있는 "어느 길이든 지킬 규칙" 5개가 **앱이 화면에서 해주지 못하고 있는 일의 목록**입니다.

| 스킬 문서에 적힌 규칙 | 이것이 뜻하는 앱의 결함 |
|---|---|
| "**이름이 열쇠다.** 이름이 다르면 조용히 어긋난다 — 넣기 전에 기존 목록을 먼저 읽어서 맞춰본다" | **조용한 실패(silent failure).** 앱이 매칭 실패를 화면에서 알리지 않는다. 가장 심각 |
| "이미 있는 것을 덮지 않는다. 특히 student_textbooks는 이미 있는 짝을 건드리면 진도 시작일이 어긋난다" | 덮어쓰기 위험을 앱이 사전에 경고하지 않는다 |
| "지우지 않는다. 삭제 대신 상태 변경을 쓴다" | 설계는 옳으나 **화면이 그 원칙을 스스로 드러내지 못한다** |
| "모르면 만들지 말고 보고한다" | 없는 학생·교재가 들어올 때의 처리 방침이 화면에 없다 |
| "대량 작업 전에 몇 건이 들어가고 몇 건이 건너뛰는지 미리 세어서 보여준 뒤 실행한다" | **미리보기가 앱에 없다.** 사람이 대신 세고 있다 |
| "열 이름을 추측하지 말고 **양식을 먼저 내려받아** 머리줄에 맞춘다" | 업로드 화면이 무엇을 요구하는지 화면에서 안 보인다 |
| "저장 후 **알림창(alert)** 이 뜨면 브라우저 조작이 멈춘다 — 원장님께 확인을 눌러달라고 한다" | 모달 남용 |

> **이 규칙들이 문서에 적혀 있다는 사실 자체가, 그 일을 화면이 못 하고 있다는 증거입니다.**
> 규칙 하나를 앱이 화면에서 해결할 때마다 문서에서 한 줄이 지워집니다. 이 문서가 0줄이 되는 것이 목표입니다.

## 2. P0 — 지금 고칠 것 (설명문을 가장 많이 없앤다)

### P0-1. 업로드 미리보기 — 조용한 실패를 없앤다

**현상**: 이름 매칭이 어긋나도 앱이 알리지 않는다. 그래서 "넣기 전에 기존 목록을 먼저 읽어서 맞춰보라"는 규칙이 문서로 존재한다.

**원인**: 1층(위치)이 아니라 **피드백 부재**. Carbon의 표현으로는 "막다른 길(dead end)"이며, 조사한 학원관리 제품 리뷰에서 반복 불만 1·4위가 정확히 이 계열입니다 — *"결제정보 변경에서 더이상 탭이 안되는 이유는 뭔가요?"*, *"수정이나 바로 취소 가능하게 해주세요 ㅠㅠㅠㅠ"*

**개선 방향**
- 파일을 고르면 **저장 전에 판정 결과를 표로 보여준다**: `들어감 N건 / 건너뜀 N건 / 이름 못 찾음 N건`
- 못 찾은 이름은 목록으로 보여주고, **가장 비슷한 기존 이름을 옆에 제시**한다 (예: `박윤찬 → 박윤찬?`)
- 「N건 저장」 버튼은 이 표를 본 뒤에만 눌린다
- 이 화면 하나가 스킬 문서 규칙 1·2·4·5를 전부 대체한다

### P0-2. alert() 제거

**현상**: 저장 후 알림창이 뜨고, 페이지가 초기 상태로 돌아가 결과 메시지가 안 보인다.

**근거**: Carbon 알림 규범 — 모달은 **"가장 방해적이며, 즉각 주의가 필요한 중대 정보에만"** 씁니다. 저장 성공은 여기에 해당하지 않습니다. 또 "절대 막다른 길로 유도하지 말 것"에 정면으로 걸립니다.

**개선 방향**
- 성공 → **인라인 알림 또는 토스트**(2~3줄 이내). 모달 금지
- 저장 후 페이지를 초기화하지 말고 **결과 요약을 그 자리에 남긴다**: `8/19 숙제 23건 저장 · 발송 0건` + 「결과 보기」 링크
- 지금은 결과를 `/report?d=...&t=hw`에서 따로 확인해야 하는데, 이 별도 확인 절차가 곧 설명문의 원인이다

### P0-3. 「양식 다운로드」를 화면 안으로

**현상**: 업로드 전에 양식을 내려받아 열 이름을 맞춰야 한다.

**근거**: 빈 상태(empty state)는 설명문의 정식 대체재입니다. Polaris 규범 — 제목은 **행동 지향**, 버튼은 **{동사}+{명사}**, primary action은 **1개**.

**개선 방향**
- 업로드 영역에 **요구하는 열 이름을 그대로 표로 표시**한다. 파일을 고르기 전에 보인다
- 「양식 다운로드」는 그 표 아래 보조 링크로 내린다 (primary 아님)
- 빈 상태 문구 예: 제목 `숙제를 엑셀로 올리기` / 본문에 열 표 / 버튼 `파일 고르기`

### P0-4. 한 화면 한 과업 — /textbooks 분리

**현상**: `/textbooks` 한 화면에 버튼이 3개다 — 「＋ 엑셀로 추가」 「＋ 단원 엑셀로 추가」 「＋ 루틴 엑셀로 추가」

**문제 두 가지**
1. **한 화면에서 세 가지 다른 대상**(교재 / 단원 / 루틴)을 다룬다
2. 라벨에 **수단(엑셀)** 이 들어가 있다. 조사한 7개 제품 중 라벨에 입력 수단을 넣은 제품은 없다

**근거**: Polaris는 목록(Resource index)과 상세(Resource details)를 짝으로 쓰라고 명시합니다. 단원과 루틴은 **교재에 속한 것**이므로 교재 목록과 같은 층에 있으면 안 됩니다.

**개선 방향**
- `/textbooks` = **교재 목록 한 가지만.** 1컬럼, 우상단에 「교재 추가」 하나
- 교재를 클릭 → 교재 상세(2컬럼, 좌측 2/3) → 그 안에 **단원 / 루틴** 탭
- 단원·루틴 업로드는 해당 교재 안에서만 가능해지므로 "어느 교재의 단원인지" 설명이 필요 없어진다
- 이것이 Google Classroom이 1차 메뉴 4개로 버티는 구조와 같다 (**대상 선택 → 대상 안의 작업**)

## 3. P1 — 대형 확장 전에 반드시

### P1-1. 1차 메뉴 재편

**현재**: `/students` `/textbooks` `/homework` `/progress` `/import` `/report` (6개)

**문제**
- `/import`는 **개발 용어**이며, 노션 옛 자료를 옮기는 **일회성 작업**이다. 조사한 7개 제품 전부 주 행동·부가 작업이 1차 메뉴 칸을 차지하지 않는다
- `/progress`(진도)와 `/homework`(학습항목)와 `/report`가 서로 무엇이 다른지 이름만으로는 갈리지 않는다

**제안**

| 현재 | 제안 | 근거 |
|---|---|---|
| /students | **학생** | 유지. 불변 코어 |
| /textbooks | **교재** | 유지. 단원·루틴은 교재 하위로 |
| /homework | **숙제** | 유지 |
| /progress | **진도** | 유지 (단, 숙제와의 경계를 화면에서 분명히) |
| /report | 학생 또는 숙제 **하위로 흡수** | 리포트는 어느 디자인 시스템에도 패턴으로 존재하지 않음 |
| /import | **설정 하위로** | 일회성 마이그레이션. 1차 메뉴 자격 없음 |

→ **1차 메뉴 4개**(학생·교재·숙제·진도) + 설정. Google Classroom과 같은 수.

**절대 규칙**: 기능이 늘어도 1차 메뉴는 늘리지 않는다. 새 기능은 기존 명사 아래로 들어간다. 조사 근거로 내비 깊이는 **2단까지**(Carbon).

### P1-2. 학생 상태를 3단계로

**현상**: 앱은 "재원생" 중심이고, 삭제 대신 상태 변경(중단·끝냄)을 쓴다. 설계 방향은 옳다.

**근거**: 클래스업은 `퇴원 = 임시 휴학`, `탈퇴 = 영구 삭제(복구 불가)`로 씁니다. 현장 의미와 정반대이고, **복구 불가능한 동작이 의미가 약한 신조어에 걸려 있는** 최악의 사례입니다.

**개선 방향**
- 학생 상태를 **재원 / 휴원 / 퇴원** 3단계로 고정한다 (온하이 방식)
- 휴원이 없으면 방학·유학·질병 때 퇴원 처리 후 되살리는 편법이 생긴다
- 영구 삭제가 필요해지면 그냥 `삭제`라 부른다. 신조어에 숨기지 않는다
- 교재 배정의 `중단·끝냄`은 학생 상태와 **다른 축**이므로 용어를 겹치지 않게 유지한다

### P1-3. 역할 분리 (강사가 생기기 전에)

**근거**: 조사 결과 국내 학원관리 제품의 공통 규범은 **원장 → 운영자 → 강사 3단계**이며, **매출·학원비 합계는 원장만 봅니다.** 어나더클래스에 「운영자에게 학원비 합계 숨기기」 기능이 실제 요청으로 만들어져 있습니다.

**개선 방향**
- 지금 데이터 모델에 역할을 넣는다. 나중에 얹기가 가장 어렵다
- 역할이 바뀌면 메뉴가 늘어나는 게 아니라 **보이는 화면이 통째로 교체**된다 (Classroom 뷰 전환기 방식)
- 강사에게 보이는 1차는 2~3개(숙제·진도)로 줄어든다 → **역할 분리 자체가 설명문을 없애는 장치**

### P1-4. 일괄 처리의 기본 단위

**근거**: 학원조아 *"월별로 반을 선택하여 일괄적으로 수강료 발생"*, 온하이 "자동 앱 청구". **학생 한 명씩 처리하는 UX는 현장을 모르는 설계**라는 것이 업계 공통입니다.

**개선 방향**
- 숙제 배포·진도 입력의 기본 단위를 개인이 아니라 **그룹(반 또는 수업 시간대)** 으로 둔다
- 클로이영어는 개별진도 방식이므로 "반"이 맞지 않을 수 있다 → **어떤 축으로 묶을지 결정 필요**(§6 확인 항목)

## 4. P2 — 여유 있을 때

### P2-1. 목록 화면에 검색·필터를 미리 넣지 않는다

문서상 명시된 유일한 수치는 **Polaris의 "목록 50개 초과 시 페이지네이션"** 뿐입니다. "N개 이상이면 검색을 붙여라"는 규정은 어느 디자인 시스템에도 없습니다.

→ 기능은 만들되 **임계값 전까지 화면에 노출하지 않는다.** 현재 규모에 불필요한 요소를 미리 띄우는 것이 설명문을 유발하는 대표 경로입니다.

### P2-2. 파괴적 동작 3단계

Carbon 규범: 저영향 = 즉시 / 중영향 = 안내하며 확인 / **고영향 = 리소스 이름을 직접 타이핑하게 요구 + danger 모달**

→ 진도 시작일이 어긋나는 덮어쓰기는 **중~고영향**입니다. 지금은 이 판단을 사람이 문서로 하고 있습니다.

### P2-3. 접근성

- 본문 대비 **4.5:1**, 큰 글자(**24px 이상** — 18px 아님) **3:1** (WCAG 2.2 AA)
- **다크 단독 테마 금지.** 앱스토어 리뷰 원문: *"블랙버전말고 화이트 버전도 만들어 주셨으면… 노안인 저는 보기가 많이 힘들어요"*
- 권한상 보기만 가능한 항목은 `disabled`가 아니라 **`read-only`**. disabled는 스크린리더가 읽지 않고 대비 기준도 통과하지 못한다

### P2-4. 공지 텍스트 저장

현재 하원숙제 이관 시 공지 텍스트가 저장되지 않습니다. 학부모 소통 이력이 끊기는 지점이므로, 저장하지 않기로 결정한 것이라면 **화면에서 그렇게 보여야** 합니다(입력칸을 아예 두지 않거나, 저장 안 됨을 상태로 표시).

## 5. 메뉴·라벨 규칙 (확정)

| 규칙 | 근거 |
|---|---|
| 1차 메뉴는 **명사**만. 동사형(`~하기`)은 버튼에만 | 조사한 7개 제품 전부. Shopify는 개발자 문서에 *"Use nouns instead of verbs"* 로 명문화 |
| 한국어 라벨은 **2~5자** | 국내 제품 실측 수렴값 |
| 라벨에 **수단**(엑셀·파일·업로드)을 넣지 않는다 | 7개 제품 중 사례 없음 |
| 1차 메뉴에 **설명문을 붙이지 않는다** | 조사한 7개 제품 중 설명문을 단 제품 **0개** |
| 설정은 업무 메뉴와 같은 줄에 두지 않는다 | 하단 고정 / 별도 영역 / 우상단 프로필 — 전 제품 공통 |
| 주 행동 버튼은 1차 메뉴 칸을 차지하지 않는다 | 전 제품 공통 |
| 개발 용어 노출 금지 | `이관` `임포트` `파싱` `싱크` `레코드` |

## 6. 실행 순서

```
1주차  P0-2 alert 제거 + 결과를 그 자리에 남기기   ← 가장 싸고 체감이 큼
2주차  P0-3 업로드 화면에 열 표 노출
3~4주차 P0-1 업로드 미리보기 (들어감/건너뜀/못찾음)  ← 스킬 문서 규칙 4개를 한 번에 제거
5주차  P0-4 /textbooks 분리 (교재 목록 → 교재 상세 안에 단원·루틴)
6주차  P1-1 1차 메뉴 4개로 재편 + /import를 설정 하위로
이후    P1-2 학생 상태 3단계 → P1-3 역할 분리 → P1-4 일괄 단위
```

**검증**: 각 단계마다 **첫 클릭 테스트**를 한다. 과업 문장만 주고 첫 클릭을 관찰한다. 첫 클릭이 맞으면 과업 성공률 **.87**, 틀리면 **.46** (Bailey & Wolfson, 실사이트 기준). 과업 예시 — "8월 19일에 숙제 보낸 거 확인해 주세요", "이 교재에 3단원을 추가해 주세요".

**진척 측정**: `chloe-english-app` 스킬 문서의 "지킬 규칙" 줄 수를 센다. 줄이 줄어든 만큼 앱이 좋아진 것이다.

## 7. 확인이 필요한 것 (추측하지 않음)

화면을 직접 보지 못한 상태에서 코드 구조와 문서로만 판단한 항목입니다.

1. **현재 각 화면에 실제로 붙어 있는 설명문의 위치와 내용** — 원장님이 "너무 많다"고 한 그 문장들
2. **목록 화면이 존재하는지** — 업로드 기능 중심으로 보이는데, `/students`·`/textbooks`에 목록+상세 2계층이 있는지
3. **`/homework`(학습항목)와 `/progress`(진도)의 경계** — 이름만으로는 갈리지 않음
4. **묶음의 축** — 개별진도 방식이라 "반"이 없다면, 일괄 처리를 무엇으로 묶을지 (수업 시간대? 학교? 학년?)
5. **현재 테마** — 다크인지 라이트인지, 대비가 기준을 통과하는지
6. **강사 추가 계획 시점** — 역할 분리의 우선순위가 여기서 갈림

→ 화면 캡처를 주시면 1~3·5는 바로 진단표로 만들 수 있습니다.
