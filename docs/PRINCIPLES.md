# 설계 원칙 (반드시 지킬 것)

이 문서의 원칙은 기능보다 우선한다. 새 화면을 만들기 전에 항상 여기부터 확인한다.

---

## 원칙 1. 같은 값을 두 번 입력하지 않고, 두 벌로 출력하지도 않는다 (Single Source of Truth)

> 원장님 (2026-08-15) — 「**1번만 입력하면 그 값이 다른 곳에서 다 보이도록
> 전부 써먹어야 된다는 게 대전제야.**」

하나의 값은 **한 곳에서만 입력**하고, 나머지 화면은 그 값을 **참조**한다.

**써먹는 쪽도 원칙이다.** 두 번 입력을 막는 것만이 아니라 — 한 번 적은
값이 **쓰일 수 있는 모든 자리에 실제로 흘러야** 한다. 적어둔 학교가
학사일정에 안 붙거나, 상담에 고른 교재가 등록 때 배정으로 안 이어지거나,
안내한 교재가 기록에 안 남으면 — 입력은 한 번이어도 원칙 위반이다.
새 값을 받는 칸을 만들 때는 **「이 값을 읽어야 할 곳이 어디어디인가」 를
먼저 나열**하고 전부 잇는다 (원칙 7 의 동선 점검과 같이 한다).

**출력도 같다** (원장님, 2026-08-09). 같은 정보를 그리는 코드가 두 벌이면
언젠가 한쪽만 고쳐져서, 두 화면이 같은 값을 서로 다르게 보여준다 —
**오류는 안 나고 화면만 조용히 어긋난다.** 그래서 —

- 같은 줄·같은 문구는 **한 벌의 컴포넌트/함수**로 그린다. 묶어 볼 때와 죽
  볼 때가 같은 줄을 쓴다 (시험 목록의 ExamRow 가 그 예다).
- 같은 계산(회차 수 · 진도율 · 등급)은 lib 의 **한 함수**가 하고, 화면은
  그 결과를 받아 그리기만 한다. 화면마다 제 나름대로 다시 계산하지 않는다.
- 이미 화면에 적힌 말을 같은 자리에서 반복하지 않는다 — 묶음 머리에
  「26년 2학기 중간」 이 있으면 그 아래 줄마다 또 붙이지 않는다.

### 지켜야 할 것

- 학생 이름·연락처는 `students`에만 있고, 리포트·출결·상담은 학생을 **연결**만 한다.
- 교재/단원은 `textbooks`·`textbook_units`에만 있고, 진도·리포트는 **선택**만 한다.
- 반의 요일·시간은 `classes`에만 있고, 출석부·시간표는 그걸 **읽어온다**.
- 학생별 진도는 한 번 기록하면, 데일리리포트·월말리포트·학부모 안내가 **같은 값을 재사용**한다.

### 하지 말아야 할 것

- 노션처럼 리포트에 교재명을 **텍스트로 다시 적기**
- 반 정보를 출석부 화면에서 **또 고르게 하기**
- 같은 숙제 항목을 화면마다 **다르게 나열하기** → 항목 마스터(`homework_items`) 하나만 사용

### 자동으로 흘러가야 하는 값

| 한 번 입력 | 자동으로 쓰이는 곳 |
|---|---|
| 학생 정보 | 출석부 · 리포트 · 상담 · 학부모 안내 · 로그인 계정 |
| 반 요일/시간 | 오늘 수업 목록 · 출석부 · 시간표 · 보강 안내 |
| 교재·단원 | 진도 입력 · 리포트 진도 문구 · 교재별 진도 현황 · **숙제 배정(대/중/소단원·분량)** · **학생별 단원 진도 체크** |
| 반에 붙인 교재 | 그 반 학생 전원의 교재 배정 · 진도 화면 · 숙제 배정 시 기본 교재 |
| 오늘 진도·숙제 | 데일리리포트 문구 · 다음 수업 숙제 · 월말 리포트 |
| 신규 상담 정보 | 상담 일정 · 레벨테스트 안내 문자 · **등록 시 재원생으로 그대로 이관** |
| 학생에게 배정한 교재 | 진도 화면 · 숙제 배정 · **교재 구매 안내 문자(목록·교재비·링크)** |
| 출결 기록 | 월별 출결 집계 · **보강 잡을 것 목록** · 수강료 보강 필요 횟수 |
| 테스트 점수 | 리포트 문구 · 성적 추이 · 재시험 대상 추출 |

### 일정(tasks)이 상위 개념이다

하나의 일정에서 세 가지가 파생된다. 같은 내용을 세 군데 적지 않는다.

| 일정에 적는 것 | 파생되는 것 |
|---|---|
| `deliver_body` | 학생 전달사항 (하원 전 전달 체크) |
| `notice_body` | 학부모 공지 (리포트에 실림) |
| `absence_student_ids` + 기간 | 결석 예정 (수업 있는 날만 자동으로) |

예) "8/1~8/3 가족여행 (홍길동)" 일정 하나 → 그 학생 수업일만 결석 예정으로 깔린다.

### 학생·학부모도 직접 넣는다

`requests` 로 결석·보강·문의를 학생/학부모가 직접 보낸다.
선생님이 대시보드에서 **확인**을 누르면 그 기간이 결석 예정으로 반영된다.
학원이 받아 적는 단계가 없어진다.

### 시험 일정은 두 번에 걸쳐 들어온다

학교가 알려주는 순서가 그렇기 때문에 입력도 두 단계로 받는다.

| 단계 | 아는 것 | 앱이 하는 일 |
|---|---|---|
| 1차 | 시험 **기간**만 | 그 기간 정규수업 = **결석 예상** → 반 전체 결석 예정 일괄 등록 |
| 2차 | **영어 시험일** | 그 **전날** = 정규수업이 아니어도 등원 → 등원 일정 + 전달사항 자동 생성 |

### 회차는 미리 보고 결정한다

앞으로 3개월 회차를 미리 계산해 알려준다.
- **기준보다 많은 달** (9회 등) → 그냥 하면 서비스, 쉬려면 그 자리에서 휴강 지정
- **기준보다 적은 달** (7회 등) → 보강 필요 횟수로 알림
매달 달력을 세어보지 않아도 되게 한다.

### 휴강은 깎지 않고 보강으로 채운다

휴강으로 회차가 빠져도 **수강료는 그대로 받는다.** 대신
- 학생별 **보강 필요 횟수**를 계산해 보여준다
- 보강을 못 해줄 경우를 위해 **차액**도 함께 계산해둔다 (다음 달에 덜 청구할 때 참고)
- 달 중간 등원·퇴원은 안 온 수업이므로 그만큼만 청구한다

### 결석은 "미리 연락받았는지"를 남긴다

새 상태값을 만들지 않는다. `attendance.status = 'absent'` 에 `planned = true` 와 `reason` 을 더한다.
- 미리 연락받은 결석 → 그날 오늘 수업 화면에서 **기다릴 필요 없는 학생**으로 접힌다
- 당일 무단 결석과 구분되어 집계된다
- 보강일을 잡으면 그 날짜 행에 `makeup_of` 로 원 결석일이 들어간다

### 오늘이 아닌 날도 미리 쓴다

`미리 작성`(`/plan`) 화면에서 날짜를 골라 숙제 · 결석 예정 · 공지 · 전달사항을 넣어둔다.
그날이 되면 오늘 수업 화면에 그대로 나타난다. 같은 값을 그날 다시 입력하지 않는다.

### "사용중"은 두 층이다

| 어디 | 뜻 |
|---|---|
| `textbooks.status` | **학원 차원** — 사용중 / 절판 / 중단 |
| `student_textbooks.status` | **학생 차원** — 사용중 / 끝냄 / 중단 |

학생이 끝낸 교재는 숙제 배정·진도 화면에서 빠지고, **재원생 기록에만** 사용기간과 함께 남는다.

### 진도는 "끝낸 것만 기록한다"

단원을 학생별로 복사해두지 않는다. 교재 단원은 `textbook_units` 한 곳에만 있고,
학생이 끝낸 단원만 `student_unit_progress` 에 한 줄씩 쌓인다.
줄이 없으면 아직 안 한 단원이다. 그래서 **순서와 상관없이** 아무 단원이나 체크할 수 있고,
건너뛴 단원이 진도를 막지 않는다.

진도율 = 완료한 단원의 분량 ÷ 전체 단원의 분량 (분량이 없으면 단원 개수 기준).

## 원칙 2. 화면은 두 유형으로 나눈다

모든 화면을 "이동 없이"로 만들면 오히려 복잡해진다. **용도에 따라 기준이 다르다.**

### 유형 A — 수업 중 화면 (이동 최소화가 최우선)

수업 시간에 선생님이 보는 화면. 화면을 옮길 여유가 없고, 한눈에 안 들어오면 못 쓴다.

**대상:** 오늘 수업 관리, 출석·리포트 입력

**규칙**
1. **한 화면에서 그날 일이 끝난다.** 페이지 이동·새 창 없음.
2. **한 번에 보이는 데이터를 줄인다.** 전체를 다 띄우지 않고 **토글로 나눠 본다.**
   - `등원예정` / `등원함` / `결석` / `보강` 상태별 토글
   - 기본은 "등원예정"만 보여주고, 처리한 학생은 목록에서 빠진다
3. **오늘·지금 기준으로 자동 필터.** 요일과 수업시간을 계산해 지금 수업할 반만 띄운다.
4. **정규수업과 보강을 함께** 본다. 보강 오는 학생도 오늘 등원자에 포함된다.
5. 클릭 수를 줄인다. 출석 체크는 **한 번의 탭**으로.

### 유형 B — 관리 화면 (DB 구조의 효율이 최우선)

데이터를 정비하는 화면. 수업 중에 쓰는 게 아니므로 **이동해도 된다.**

**대상:** 교재·단원, 재원생, 반(수업) 관리

**규칙**
1. **구조의 정확성이 우선.** 화면 편의를 위해 데이터를 중복시키지 않는다.
2. 필요하면 화면을 나눠도 된다. 대신 **엑셀 업로드**로 대량 입력을 지원한다.
3. 목록은 항상 **전체/일부 선택 → 수정·삭제·변경·이동**.

## 오늘 수업 화면 설계 (유형 A의 핵심)

### 전제: 10명이 넘으면 표는 못 쓴다

등원 학생이 10명 이상이면 학생 줄 × 항목 열의 큰 표는 **실제로 안 읽힌다.**
눈이 어디 있는지 놓치고 머릿속이 복잡해진다. 그래서 두 가지 모드로 나눈다.

| 모드 | 언제 | 형태 |
|---|---|---|
| **한 명 카드** (기본) | 학생이 등원할 때 | 화면에 **한 명만** 크게. 처리하면 다음 학생으로 |
| **명단 보기** | 전체 현황 확인 | 이름·상태만 있는 짧은 줄. 입력칸 없음 |

### 왜 "한 명씩만"이 아니라 "목록 + 펼치기"인가

한 명씩 순서대로 넘기는 방식은 **학생이 순서대로 오지 않는다**는 현실과 안 맞는다.
지금 눈앞에 있는 학생을 바로 처리할 수 있어야 한다.

그래서 **처리할 학생은 전부 보이되, 한 줄로만 보이게** 한다.
- 목록은 이름·반·상태만 있는 **한 줄** → 15명이어도 훑어진다
- 학생을 누르면 **그 자리에서 펼쳐져** 입력칸이 나온다 (한 번에 하나만 펼침)
- 저장하면 접히면서 **완료 칸으로 내려간다**
- 완료된 학생은 기본으로 **접혀 있고**, 숫자만 보인다 (`완료 8명 ▸`)

즉, **화면에 늘 보이는 건 "아직 처리 안 한 사람"** 뿐이다.
일이 끝날수록 화면이 저절로 비워진다.

### 화면 구조

```
오늘 · 7월 25일 (금)                      남은 6명 · 완료 8명
[전체] [등원예정] [결석] [보강]
────────────────────────────────────────────────────
▾ 금 5:00-7:30  기본반 · 1강의실                    남은 4명

  홍길동   중2                                      [등원]  ▸
  ┌──────────────────────────────────────────────┐
  │ 출결   [정시] [지각] [결석] [보강]              │  ← 펼친 학생만 크게
  │ 단어   [__]/20      문장  [__]/10              │
  │ 숙제   ○ 독해  △ 워크북  ✕ 단어(온라인)         │
  │ 진도   Unit 3  (지난 수업에서 이어짐)            │
  │                              [저장]            │
  └──────────────────────────────────────────────┘
  김철수   중3                                      [등원]  ▸
  이영희   중2   보강                               [등원]  ▸

▸ 완료 8명

▸ 금 7:30-10:00 심화반 · 2강의실                    남은 2명
```

**동작 정리**
1. 처리할 학생은 **전부** 한 줄로 보인다. (숨기지 않음)
2. 누르면 그 줄이 펼쳐지고, 다른 줄은 접힌다.
3. 저장하면 접히고 **완료 칸으로 이동** → 남은 목록이 줄어든다.
4. 완료 칸은 기본 접힘. 고칠 일 있으면 펼쳐서 수정.
5. 반은 시간순, 지금 시간대 반이 자동으로 펼쳐진다.
6. 보강 학생은 원래 반이 아니어도 오늘 목록에 뜨고 **보강 표시**가 붙는다.
7. 출결만 빠르게 찍고 싶으면 줄의 **[등원] 버튼 한 번**으로 끝난다.
   (점수·숙제는 나중에 펼쳐서 입력)

> 원칙: **선생님이 판단할 것을 화면이 대신 좁혀준다.**
> 전부 보여주고 고르게 하지 않는다.

## 원칙 3. 자동화는 데이터가 흐르게 만드는 것

발송이나 알림보다, **한 번 입력한 값이 다음 단계로 저절로 넘어가는 것**이 먼저다.

| 흐름 | 자동 처리 |
|---|---|
| 수업 입력 → 리포트 | 문구 자동 생성 (선생님은 확인만) |
| 오늘 숙제 → 다음 수업 | 미제출 항목이 다음 수업 화면에 자동 표시 |
| 출결 → 안내 | 결석 시 보강 안내 대상 자동 추출 |
| 테스트 미통과 → 재시험 | 재시험 대상 목록 자동 생성 |
| 진도 → 교재 종료 예상 | 남은 단원으로 교재 소진 시점 자동 계산 |

## 원칙 4. 고치기 전에, 전체와의 정합성을 검토한다

> 원장님 (2026-08-09) — 「한국 학원 시스템에 대한 이해 없이 내 요구를
> 단편적으로 반영하다 보니 예외 규칙이 너무 많아져서 제대로 작동이 안 되는
> 것 같아.」 — 실제로 그랬다. 시험 이름 분류가 두 파일에 두 벌로 있었고,
> 받아오기는 잘못 하나마다 땜질 규칙을 하나씩 붙인 누더기였다.
> **요청 하나를 반영할 때마다, 그 수정이 전체 설계와 맞는지 먼저 본다.**

수정 하나를 넣기 전에 반드시 거치는 순서:

1. **같은 판단이 이미 있는지 찾는다.** 새 함수·새 정규식·새 목록을 쓰기
   전에 grep 으로 기존 것을 찾는다. 있으면 그곳을 고치거나 가져다 쓴다 —
   비슷한 것을 하나 더 만들지 않는다. (판단이 사는 곳 목록:
   `docs/시험-일정-조사.md` §7, `scripts/check-dup.mjs` 의 ONE_PLACE)
2. **규칙을 고치면 소비처를 전부 찾는다.** 그 함수·그 값을 읽는 모든
   자리를 grep 으로 나열하고, 하나하나 이번 수정과 어긋나지 않는지 본다.
   한 곳만 고친 규칙은 안 고친 것보다 나쁘다 — 두 화면이 다른 말을 하는데
   오류는 안 난다.
3. **예외를 추가하기 전에 멈춘다.** 「이 경우만 다르게」 가 세 번째로
   필요해지면, 그것은 예외가 아니라 **설계가 틀렸다는 신호**다. 규칙
   자체를 다시 세운다. (받아오기를 땜질 셋에서 「이번 목록에 없는 나이스
   줄은 치운다」 하나로 바꾼 것이 그 예다.)
4. **도메인부터 확인한다.** 학교·시험·수강료처럼 실제 세계의 규칙이 걸린
   수정은, 코드를 만지기 전에 그 세계가 실제로 어떻게 돌아가는지 먼저
   조사한다 (`docs/시험-일정-조사.md` · `docs/영어시험-특징.md`).
5. **고친 뒤에는 전수 검사 + 실제 화면.** `bash scripts/check-pages.sh` 와
   `bash scripts/e2e/run.sh` 를 돌리고, 화면이 걸린 수정이면 브라우저로
   찍어서 눈으로 본다. 빌드가 통과해도 화면은 터질 수 있다 (실제로 그랬다).
6. **한 곳으로 모은 규칙은 등록한다.** 새로 뽑아낸 공용 규칙은
   `scripts/check-dup.mjs` 의 ONE_PLACE 에 한 줄 올려서, 다시 흩어지면
   검사가 잡게 한다.

## 원칙 5. 그 밖의 확정 사항

1. 화면을 만들기 전에 **DB 속성을 나열하고 불필요한 것을 제거**한다.
2. 입력은 **엑셀 양식 다운로드 → 파일 업로드**를 기본으로 한다.
3. 모든 목록은 **전체/일부 선택 → 수정·삭제·변경·이동**이 가능해야 한다.
4. 학생 로그인 아이디는 `chloe + 전화 뒷자리 4`, 충돌 시 `-2`, `-3`.
   기본 비밀번호 `0000`, 첫 로그인 후 학생이 변경.
5. 노션의 수식·롤업·버튼은 저장하지 않고 앱 기능으로 대체한다.
6. 자주 바뀌는 항목(숙제 종류 등)은 컬럼이 아니라 **마스터 테이블**로 둔다.
7. UI 문구는 **선생님이 쓰는 말**로 쓴다. (설명용 단어를 화면에 그대로 쓰지 않기)
8. 여백보다 **한 화면에 담기는 정보량**을 우선한다.

## 원칙 6. 속도 — 왕복은 파도로, 반응은 즉시 (2026-08-14 확정)

> 원장님: 「전반적으로 버튼입력속도, 모든 페이지의 로딩 자체가 느려」 ·
> 「0.1초 만에 반응하는 걸 목표로 삼아」

느림의 원인은 코드가 무거워서가 아니라 **DB 왕복을 한 줄씩 차례로 기다려서**였다.
오늘 수업이 53회를 직렬로 기다렸고, 클릭 하나에 인증 왕복이 기본요금으로
붙었다. 아래는 그걸 걷어낸 구조다. **앞으로 어떤 구조 변경도 이 전제를
훼손하지 않는다** — 기능을 더하다 직렬로 되돌리는 것이 제일 쉬운 퇴행이다.

### 6-1. 페이지 조회는 파도(wave)로 묶는다
서로 필요한 것이 없는 조회는 `Promise.all` 한 층으로 보낸다.
의존이 있으면 층을 나눈다 (파도 1 → 그 결과가 필요한 파도 2 → …).
- 새 조회를 페이지에 더할 때는 **기존 파도에 태우는 것이 기본**이다.
  파도 밖에 `await supabase` 를 한 줄 더 놓는 순간 층이 하나 늘어난다
- 사다리 폴백(옛 DB용)은 예외 — 실패했을 때만 도는 길이라 직렬이어도 된다
- 적용된 화면: 오늘 수업 · 재원생 · 교재 · 달력 · 출결 (구조는
  `app/today/page.jsx` 의 파도 주석이 표본)

### 6-2. 로그인 확인은 쿠키로 — 인증 서버에 다시 묻지 않는다
`auth.getUser()` 는 부를 때마다 인증 서버 네트워크 왕복이다. 어디서든
`lib/session.js` 의 `sessionUser()` 를 쓴다 (쿠키만 읽는다, 왕복 0).
**검증을 버린 것이 아니다** — uid 로 하는 일은 결국 전부 DB 조회·수정이고
그 요청에 같은 토큰이 실려 간다. 위조면 PostgREST 가 서명에서 거절한다.
미들웨어의 역할 확인도 같은 이유로 쿠키 캐시(1시간)다 — 길목은 예의,
자물쇠는 RLS.

### 6-3. 누른 반응은 0.1초 — 화면을 먼저 바꾸고 저장은 뒤에서
서버 왕복은 아무리 줄여도 0.1초가 안 된다. 자주 누르는 칩·토글은
**낙관적**으로 한다: 로컬에 먼저 칠하고(paint) → 저장 → 실패하면 되돌리고
알린다. 적용된 곳: 출결 찍기 · 숙제 검사 ○△✕ · 진도 칩.
새로 만드는 「하루에 수십 번 누르는 자리」는 이 방식이 기본이다.

### 6-4. 모든 화면이 내는 세금은 기억해 둔다
메뉴 배지처럼 화면마다 도는 셈은 20초 메모(배포에서만)로 막는다.
검사가 가짜 DB 로 여러 번 부르는 것과 안 섞이게, 메모는
`NODE_ENV === "production"` 에서만 켠다.

### 지키는 검사
`scripts/check-speed.mjs` — 파도가 풀리거나(직렬 개수 늘어남),
`auth.getUser` 가 새로 들어오거나, 낙관 패턴이 사라지면 잡는다.

## 원칙 7. 손대기 전에 계획 → 동선 점검 → 재계획 (2026-08-14 확정)

> 원장님: 「대전제 다시 추가해. 항상 계획을 잔뒤, 전 페이지를 다 사용할
> 때의 동선과, 중복, 누락, 불필요에 대한 가능성을 고려한 뒤, 예상되는
> 문제점을 찾고 다시 계획을 세운 뒤 피드백 받거나 실행한다.」

바로 코드를 치지 않는다. 순서를 건너뛰면 원칙 4(정합성)가 지켜지고 있는지
스스로도 모른 채로 고치게 된다.

1. **먼저 계획을 세운다** — 무엇을 어디에 어떻게 바꿀지 (파일·함수·화면
   단위로) 말로 먼저 정리한다.
2. **그 페이지를 실제로 처음부터 끝까지 쓴다고 상상하며 동선을 짚는다** —
   원장님이 이 화면에 들어와서 나갈 때까지 누르는 순서. 그 동선 위에서:
   - **중복** — 같은 것을 두 번 입력·표시하게 만들지 않는가 (원칙 1)
   - **누락** — 이 변경이 건드리는 다른 화면·다른 목록에 반영이 안 빠졌는가
     (같은 표를 읽는 자리를 grep 으로 다 찾았는가 — 원칙 4-2)
   - **불필요** — 이 화면·이 버튼이 지금 하는 일과 안 맞거나, 이미 있는
     길과 겹치지는 않는가
3. **예상되는 문제점을 미리 찾는다** — 이 순서로 썼을 때 막히는 지점,
   빈 상태(자료가 없을 때), 잘못된 입력이 들어왔을 때를 구체적으로 짚는다.
4. **2·3에서 나온 것으로 계획을 다시 세운다.**
5. **그 다음에** 피드백을 받거나(애매하면 여쭙는다) 실행한다.

무엇을 고칠지 뻔한 아주 작은 수정(오탈자·색 하나)까지 이 순서를 다 밟을
필요는 없다 — 그런데도 **"이 화면을 실제로 써보면 어떨까"를 한 번은
스스로 짚고 넘어간다.** 이번 세션에 여러 번 실제로 걸렸던 문제들
(진도 판이 페이지로만 나오는 이유가 안 보였던 것, 대단원 통째로 선택이
안 됐던 것)이 전부 **동선을 끝까지 안 밟아봐서** 생긴 틈이었다.
